# 회원 상세 — 프로필 항목 (성별 · 소셜 · Steam · 계정 통합 · 정책 동의)

현재 회원 상세 응답(`member_view`)에 없는 계정 정보 항목이다. 신규 API 계약(임시)이며 mock으로 화면을 확인한다.

- 구현: `src/renewal/entities/member-profile`, mock `src/renewal/mocks/member-profile.ts`, 화면 `screens/member-detail`
- mock 등록: `src/shared/mocks/handlers.ts`에 한 줄 추가(리뉴얼 격리 원칙의 예외)

## 신규 API 계약
`GET /admin/member/profile?m_no=`

```json
{
  "gender": "여성",                       // "남성" | "여성" | null
  "socials": ["네이버", "카카오"],         // 연동된 소셜(없으면 [])
  "steam_linked": true,                   // true | false | null(정보 없음)
  "merge": {                              // 계정 통합 이력, 없으면 null
    "merged_at": "2026.09.30 14:00:00",
    "detail": { "result": { ... }, "sources": [ ... ] }   // AccountMergeDetail(entities/member-profile)
  },
  "policies": { "terms": true, "privacy": true, "marketing": false }   // 없으면 null
}
```
- 값이 없으면 화면은 `-`로 표시한다. 계정 통합 상세 버튼은 `merge`가 있을 때만 보인다.
- 기존 응답의 `sns_type`(가입 방법 1개)은 `socials`가 비어 있을 때의 대체 표시로만 쓴다.
- `policies.marketing`은 legacy `mailling`(뉴스레터 수신 동의)과 대응한다.
- 실제 API에서는 별도 조회 대신 회원 상세 응답에 포함하는 편이 자연스럽다.

# mock 회원 데이터 (50명)

기존 8명 + 생성 42명(`src/shared/mocks/db/member-seed.ts`, m_no `100300`~`100341`). 회원 내역 목록은 30명씩 2페이지로 보인다.

| 구분 | 계정 | 내용 |
|------|------|------|
| **전체 필드 계정 20명** | m_no `100300`~`100319` | 이메일·휴대폰·생년월일·소셜·성별·Steam·정책 동의가 모두 있고 주문·등급 변동 이력·리뷰가 있다. 생년월일은 6자리/8자리를 번갈아 사용. 짝수 번째(100300, 100302…)는 **계정 통합 이력**도 있다. |
| 부분 계정 22명 | m_no `100320`~`100341` | 이메일/휴대폰/생년월일 중 일부가 비어 있고(14명), 성별·Steam·계정 통합·정책 동의는 대부분 없다. 빈 값(`-`) 표시 확인용. |

- **페이지네이션 확인**: `100300`은 주문 25건·리뷰 25건(20개 초과)이다.
- **이메일 미인증(수동승인 버튼)**: 4명 중 1명(index % 4 == 3) — 기존 3명 포함 13명.
- 등급은 1/2/3이 14명씩, 유형은 일반(P) 30·리셀러(R) 6·휴면(S) 4·이벤트(E) 2. 휴면 회원은 최근 접속이 2023년.
- 주문 상태는 주문완료(2)·구매확정(6)이 대부분이고 취소요청(8)·취소완료(9)가 섞여 있다. 주문 내역의 "주문완료" 칩은 2~6, "주문취소" 칩은 8·9로 거른다.
- 모든 값은 결정적으로 생성되어 새로고침해도 같다(승인·잠금·삭제 같은 변경만 새로고침 전까지 유지).
